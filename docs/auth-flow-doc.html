Inventory API: how authentication works

A Django REST inventory API sits behind Kong Gateway 3.16 (managed by Konnect). Kong handles all client authentication with plugins. Browsers sign in with Auth0 and keep a Kong session cookie; scripts and apps use OAuth2 tokens; the MCP server uses an API key. Django never sees any of it: Kong always calls it with one Basic-auth service user.

  • Browser · OIDC + session
  • App · Bearer JWT
  • App · client_credentials via Kong
  • apikey · MCP

1. The big picture

Three routes on one Kong service. Each route has its own way of checking who the caller is; all of them end with DataKit adding Authorization: Basic user1 before the request reaches Django.

Solid lines carry requests; the dashed line is configuration pushed from Konnect by deck gateway sync.

2. How the OIDC route decides what to do

A single openid-connect plugin serves both browsers and machines because it is configured with four auth_methods: bearer, client_credentials, session and authorization_code. For each request it looks at what the client sent and picks the matching method.

Simplified view of the plugin's method selection. A request with no credentials at all ends in a redirect to Auth0, which is why an unauthenticated curl gets 302 rather than 401.

3. Browser: OIDC login and session

The browser never handles tokens. Kong runs the authorization-code flow (with PKCE) against Auth0, keeps the tokens inside an encrypted cookie called inventory_session, and from then on only checks that cookie.

Session rules

SettingValueEffect
session_idling_timeout900 s15 minutes without a request → log in again
session_rolling_timeout3600 sCookie is re-issued at least every hour while in use
session_absolute_timeout28800 sAfter 8 hours a new login is required, active or not
session_cookie_*Secure · HttpOnly · SameSite=LaxNot readable by page JavaScript, only sent over HTTPS
logout_uri_suffix/logoutClears the Kong session and ends the Auth0 session (RP-initiated logout)

The DRF page also loads CSS and JS from /static/…. Those requests go to the separate public /static route, since they fall outside /oidc/inventory.

4. App: Bearer JWT

The app gets its own access token from Auth0 (as the Machine to Machine application) and sends it on every call. Kong verifies the JWT locally with Auth0's public keys, so Auth0 is not called per request.

TOKEN=$(curl -s https://$AUTH0_DOMAIN/oauth/token -H 'Content-Type: application/json' \
  -d "{\"grant_type\":\"client_credentials\",\"client_id\":\"$AUTH0_M2M_CLIENT_ID\",
       \"client_secret\":\"$AUTH0_M2M_CLIENT_SECRET\",\"audience\":\"$DECK_AUTH0_AUDIENCE\"}" | jq -r .access_token)

curl -k https://localhost:8443/oidc/inventory/ -H "Authorization: Bearer $TOKEN"

5. App: client_credentials through Kong

The simplest option for scripts: send the M2M client id and secret to Kong as HTTP Basic. Kong performs the token request itself (adding the audience), then caches the token for later calls.

curl -k -u "$AUTH0_M2M_CLIENT_ID:$AUTH0_M2M_CLIENT_SECRET" https://localhost:8443/oidc/inventory/

6. apikey and MCP

The original route. Kong AI Gateway 2.2 publishes each item endpoint as an MCP tool and calls this route as its upstream, forwarding the client's apikey. The same route also works for direct curl calls (curl -k https://localhost:8443/inventory/ -H "apikey: test").

7. Where things are configured

kong/kong.yaml

decK state for control plane django-apigw: routes, OIDC, key-auth, DataKit, TLS cert.

kong/auth0.env

Auth0 issuer, client ids/secrets, audience, session secret. Gitignored; copy from auth0.env.example.

kong/ai-gateway.yaml

MCP server on Kong AI Gateway, applied with kongctl.

Auth0 dashboard

API (audience, RS256), Regular Web App, M2M App, RP-initiated logout.
